# 长卷与书信：产品理解，2026-09-22

状态：用户回复“做吧”后，长卷与账号信邮已经完成本地实现。默认每日成功投邮 3 封、收件方最短邮程 24 小时，可在邮局设置修改。下方保留方向研究；实际实现与验收边界以文末为准。

## 凯鲁亚克模式

1951 年，凯鲁亚克用接成长卷的纸打出《在路上》的早期稿，目的是免去换纸造成的中断。Lilly Library 描述实物为 119 英尺 8 英寸长、9 英寸宽，约 36.5 米 × 22.9 厘米。UMass Lowell 的 Kerouac Center 同时说明：这次连续写作之后仍有细致修订，不能把长卷误解为无需准备或编辑。

来源：

- [Lilly Library 的原稿展览说明](https://blogs.libraries.indiana.edu/lilly/2014/02/06/original-manuscript-scroll-of-on-the-road-returns-to-the-lilly-library-february-3-22/)
- [UMass Lowell：On the Road Scroll](https://jackkerouac.org/on-the-road-scroll-2/)

Typer 应保留的是思路持续流出的节奏。进入这一模式后装入连续窄幅长纸，保持现有固定击打点及回车进纸机构，写满当前可见区域不会触发页末或退纸。已经打出的纸从机器后方连续送出，有卷曲与自身投影，但不能跨过机壳或遮住当前行。

长卷不按 A4 分页，不显示“第几页”。可以安静地显示累计字数或已写纸长。用户决定何时停下；“收卷”保存当前长卷，之后可以展开阅读或重新装入继续写。保留系统中文输入法和现有机械墨迹。不会强迫用户删掉标点、禁用换行，也不会加入停顿就丢稿的惩罚。

实现边界：目前 `getPaperLayout` 和草稿载入都限定页数，导出是固定 2480 × 3508 PNG。因此不能只把纸的 CSS 高度拉长。需要独立的长卷模型与持久化，屏幕只渲染视口附近的纸和字，写到数千行时仍保持固定击打坐标。长卷阅读与导出另做分块，完整内容可以分页打印，但写作中不显示分页；不声称浏览器能生成无限高度 PNG。

验收应包含超过原有页末、长时间连续输入、重新载入续写及长卷存档；长纸回卷和全部机械状态仍要通过遮挡检查。

## 账号间书信

产品目标是让用户愿意为一个具体的人留出时间写信。每个账号拥有一个稳定的站内邮址和私人信箱，可以明确地把一封信寄给另一个账号。“邮址”首先是 Typer 内部地址，不默认承诺提供完整的互联网电子邮箱。

建议路径：

1. 选信笺，在打字机上写信；写完后校对收件人，折纸入封。
2. 在信封填写站内邮址，选择邮票，显示寄达时间后投邮。邮票体现纸张、主题与情绪；初版不把它变成付费道具。
3. 生成带寄件日期的邮戳，信件进入邮路。内容在投邮时形成快照，途中不能悄悄改写正文。
4. 收件人到期收信并拆封；看到的是保留纸张与墨迹的完整信件。回信另取一张信笺，与原信一起收藏。

建议每日限额计算“投邮成功的封数”，允许无限次写草稿。这样不会在写到一半时打断用户。可先以每日 3 封、隔日投递作为体验样本，但这两个数字仍只是建议；用户已经明确希望可设置。

设置需要有明确归属：个人可选择自己的寄信节奏，通信双方可以约定邮程；收件人的慢收信偏好不应被寄件人单方面绕过。首版适合固定邮班或明确延时，不必用不透明随机延迟。对方不需要显示在线状态或已读回执，等待本身是体验的一部分。

账号与投递必须真实：登录会话、收件人授权和送达时间由服务端核验；内容在送达前不能通过客户端接口提前取得。每日计数与投递状态需要持久化及幂等处理，重复点击或任务重试不能寄出两封。关闭浏览器不会中止邮路；客户端倒计时只负责显示。账号模块还需要明确谁可以来信、屏蔽来信的入口。

现状边界：`worker/index.js` 目前只有静态资源与 SPA 回退；稿件使用 `localStorage`。原型中的“发送成功”动画不能充当跨账号真实投递的验收。

## 先后关系

长卷主要扩展个人写作，可以在现有打字机上独立完成。书信需要先把写信、封缄和拆信的体验做成可试用原型，再接入真实账号与服务端投递。两者共用旧式纸张与墨迹，但各自拥有独立的稿件类型与完成动作，不复活作家书桌场景。


## 2026-09-22 实现

- 工作台可选择散页或凯鲁亚克模式。散页草稿沿用原来的存储；长卷按行保存在 IndexedDB，没有 A4 行数上限。可切回原稿，收卷后展开阅读、从文稿箱装回续写。屏幕渲染窗口在中文布局下保持 33 行。
- 长卷沿现有压纸机构进纸，纸与字车共用坐标，维持整机比例。扫描纸张在材质边界镜像衔接，屏幕与 PNG 使用同一处理。当前没有增加地面盘绕或悬垂纸卷的三维模型。
- 长卷导出为宽 2480 像素、高不超过 6000 像素的连续片段；超过一张时下载一个 ZIP。墨迹由原字形与每个字保存的 seed 重绘。写作本身没有这些输出分页。
- 信邮使用真实注册、登录、HttpOnly 会话和本地 SQLite。信笺仍在原来的机械打字机上书写，可选已有五种纸张。封缄时核对收件人、选择山路或归燕邮票，设置邮程后投邮。来信拆封后保留原纸张和墨迹，可另取信笺回信。
- 每日限额计算成功投邮的信，范围 1–20 封；收信最短邮程为 0–168 小时。实际送达时间取寄件人邮程与收件人最短邮程的较大值。服务器保存绝对时间，到时即进入收信箱，关闭浏览器或重启服务不会重置邮路。打开信箱时每 30 秒刷新，也可手动刷新。
- 收件人送达前不能读取信件正文；第三个账号不能访问。发送内容存为不可变快照；重复投邮使用同一编号返回原信且不重复计数。收件人可关闭新来信或屏蔽具体邮址。寄件人不获得已读回执。

## 运行与边界

开发服务器自带信邮 API。生产构建可通过 `npm start` 运行静态应用和 API，要求 Node.js 22.13+；默认监听 127.0.0.1:8787。数据库默认在 `.typer-data/post.sqlite`，该目录已忽略。可设置 `TYPER_POST_DB`、`HOST`、`PORT`；经 HTTPS 反向代理公开运行时需设置 `TYPER_PUBLIC_ORIGIN` 为实际站点源并持久化数据库。

本次只在本机实现与验证，没有发布公网。`handle@typer` 是站内邮址，不是可接收外部电子邮件的地址。浏览器内未寄草稿没有跨设备同步；账户没有找回口令流程。用户间在不同设备通信需要部署同一后端。受保护的 Sites 静态 Worker 文件保持原样，因此直接发布静态构建不会带上 SQLite 邮局。

完整测试证据位于 `output/scroll-post-2026-09-22/`；实际 Safari 验收记录见 `design-qa.md`。
